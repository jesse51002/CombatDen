Layouts you can enumerate

Thirty-four whole-screen arrangements of the CombatDen member app, written as JSX so each one is readable at a glance and diffable against its siblings. Every value of an enum carries exactly the same elements as the screen that ships today. Only the arrangement moves.

One enum per screen. Each value is one complete, reviewed arrangement.

The alternative was composable region slots: a topbar enum crossed with a schedule enum crossed with a hero enum. It is rejected because layout has no deterministic accept condition. Colour resolves against WCAG and OKLCH; there is no formula for “is this arrangement good,” so a person is the throughput ceiling and the review surface has to add rather than multiply.

Shell

app_shell_format

shared/widgets/topbar/app_topbar.dart · shared/widgets/nav/app_bottom_nav_bar.dart

The chrome that frames every screen. Factored out of the per-screen enums because it belongs to none of them: a shell value is reviewed once against one screen, then composes without changing any body. That is additive, not multiplicative.

Nav order is fixed across every value. It is muscle memory, not composition.

Motion

          
        

        

          Motion stays on the pipeline side of the boundary: assets are data, layout is code. A
          tenant's motion choice must not be able to break an arrangement, so these enums touch
          timing and entrance only. One personality resolves the whole set; five surfaces can
          override it where the brand actually shows.
        

      


      

        

          

            
Personality

            motion_personality
          

          
shared/widgets/animation/celebration_timings.dart

          

            The same three-element reveal at four timing sets. Note what is missing:
            no value uses an overshoot or elastic curve. The app's motion law is ease-out only, so
            a “hype” built on easeOutBack would be a brand change smuggled in
            as a token. Energy comes from stagger density instead.
          

        

        

          
          
          
          
        

        

          cinematic breaks the 300ms per-element ceiling. Both
          MobileApp/CLAUDE.md and PRODUCT.md state ease-out, no bounce,
          under 300ms. Either that ceiling becomes a per-personality token, or
          cinematic caps at 300ms and finds its weight in stagger and count-up length
          alone. The second keeps one motion law for the whole app and is the smaller change.

Wiring
lib/core/app_slots.dart

          

            Layout and motion are new slot kinds on the manifest that already declares colours,
            images, fonts, texts and icons. The shape follows that file's own convention exactly:
            an explicit id constant, one line in the matching list, one matching declaration in
            the service's apps/<app>/app.yaml.

          Consumption mirrors the existing accessors. A ThemeLayout.value and a
          ThemeMotion.value return the resolved enum with the shipped value as the
          fallback, so an unbranded build and a tenant missing the slot both render exactly what
          ships today. Nothing under lib/ is changed by this document.
        

      


      
      

        

          
Open questions

          
Six decisions this pass surfaced and did not make.

        

        
    
          
  1. Does posterDeck pass the gate? It pins one redeem action under a deck instead of one per card. Either the check counts actions per data row rather than per screen, or the value is cut. Worth deciding before the gate is written, because it decides whether the rule is a plain multiset diff or something that understands binding.
    2. 
          
  2. Does cinematic get to break the 300ms ceiling? Per-personality ceiling, or cap it and let stagger carry the weight. The second keeps one motion law.
    3. 
          
  3. Is sparkle_style in or out? Six surface enums instead of five, for a surface the personality currently reaches only by particle count.
    4. 
          
  4. Do markOnly and nextUpHero ship as offerable defaults? Both hold the invariant. Both hide something a tenant may specifically want visible: the gym name, and the class thumbnails.
    5. 
          
  5. How many values per screen is right? Five is what this pass produced. Human review is the throughput ceiling, so library size is a cost decision, not a design one, and it should be set deliberately rather than by whatever a generation run emits.
    6. 
          
  6. Do the two home bodies stay two bodies? HomeNotBookedBody and HomeBookedBody are near-identical trees differing by one card, so every home value has to be authored twice. Collapsing them to one body with a nullable card halves the authoring cost. Pre-existing duplication, not something this work introduced.
